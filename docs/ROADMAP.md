# 路线图

这份文件只放**还没做**的事与验收口径。已交付的能力看 [README](../README.md)
的功能表与 [DEPLOY](DEPLOY.md) 第八节的实测记录；页面上的"未生效项"说明以
设置页为准（`nw_config.UNHONORED`）。

原则（和现有代码一致）：

- 核心后端继续**只依赖 Python 标准库**。需要模型、需要推送协议这类绕不开的
  外部能力，一律做成**可选旁路**：装了就用，没装就明说降级，不能让主链路起不来。
- 前端继续 ES5 单页、无构建步骤。
- 不新增"页面有开关但代码没消费者"的设置项；没做就不放进页面。

下面是从原计划里挑出来的第 5~10 项（前 4 项已随 1.2.0 交付：直播花屏与回放秒开、
双码流、事件时间轴与检索、通知多渠道与事件段加锁、Prometheus 指标）。
顺序按"风险 × 收益"排，不承诺日期。

---

## 5. 本地 AI 检测（人形 / 车辆 / 宠物）

**要解决的问题**：现在的本地侦测只回答"画面动没动"。树影、雨雪、宠物走过都会
被算成事件，时间轴很快被噪声灌满，通知也就不敢开。

**落地要点**

- 复用现有离线链路：分段写完后只在**已判定有动静的区间**抽帧（现在就有事件窗口），
  不做全量逐帧推理。
- 推理走可选旁路：`onnxruntime` + 一个轻量检测模型（YOLO 级别的小模型），
  以子进程方式跑，CPU 占用受限、可随时关掉；装不上就退回当前的像素差分。
- 事件行增加 `labels`（如 `["person"]`）与置信度；筛选放在回放页与通知开关上
  （"只推人形/车辆"）。
- 模型文件不进仓库：许可与体积都不合适，由用户自取（和当前小米 SDK 的处理方式一致）。

**验收**

- 同一段素材：无模型时事件数与现在一致；装了模型后，`labels` 与人眼标注的
  召回/误报有可复现的对照表（至少两组白天、两组夜间）。
- 推理不装时 `/api/health`、`/api/metrics` 正常，设置页明确写"未安装模型"。
- 一段 5 分钟分段的额外耗时 < 15 秒（4 核 Xeon 基准），且不与录像/直播抢到断流。

**明确不做**：人脸识别、车牌识别、跨摄像头轨迹。这些是另一个量级的合规与算力问题。

## 6. 隐私与合规

**要解决的问题**：录像是敏感数据。现在有登录闸门与"画面不出门"，但缺少
"谁能看、看了什么、导出前遮什么"这条链路。

**落地要点**

- **隐私遮罩**：每路摄像头可画矩形区域（画面坐标），直播、回放、导出统一打码；
  遮罩配置随摄像头走，重启不丢。
- **访问审计**：登录、回放起播、录像下载、设置变更各记一行（时间/来源 IP/动作/
  摄像头），本地 JSONL 轮转，页面上可查最近 N 条；不引入数据库。
- **导出脱敏**：导出片段默认套用遮罩；导出文件名不带摄像头真名。
- **保留期硬约束**：给"最长保留"一个上限（例如 90 天），超过就不允许配置，
  免得"设置 3650 天"变成事实上的永久留存。
- 文档同步：[PRIVACY](PRIVACY.md) 增补"审计与遮罩实际做了什么、没做什么"。

**验收**

- 开遮罩后，直播流与导出文件在同一坐标区域都不含原始像素（抽帧比对）。
- 审计日志在重启后继续追加；页面上能看到最近 50 条，且普通"观看"账号看不到设置变更。
- 保留期上限在保存时被钳制，页面显示钳制后的值（延续"显示值 = 生效值"）。

**明确不做**：云端人脸库、自动给陌生人打码（误判代价太高，且需要更强的模型）。

## 7. 存储可靠性

**要解决的问题**：现在能滚删、能告警空间不足，但"盘坏了会不会提前知道"、
"删错了能不能找回"没有答案。

**落地要点**

- **SMART 体检**：定时读 `smartctl`（没装就跳过并说明），把关键属性
  （重映射扇区、待映射、温度）接进 `/api/health` 与 `/api/metrics`，
  只做只读探测，不碰磁盘策略。
- **写入校验**：分段落盘后核对时长与文件尾（`ffprobe` 已有），
  截断/0 字节段直接标坏并记流水，不留在回放列表里。
- **回收站式删除**：清理循环不直接 `unlink`，先移入 `<rec>/_trash/<日期>/`
  保留 24 小时再真删；被事件引用的段照旧留到最后。
- **备份出口**：提供一个"把某天某路的分段 + 事件索引打成一个包"的命令行工具
  （stdout 或指定目录），方便用户自己 rsync 到异地；不内置云上传。

**验收**

- 人为 kill -9 录像进程，重启后坏段被识别并隔离，回放列表不出现黑段。
- 清理后 24 小时内可在回收站找回；超过 24 小时的自动消失，磁盘占用回到预期。
- SMART 不可用（容器无权限/无 smartctl）时健康检查不因此变红，只在自检里提示。

**明确不做**：内置 RAID 管理、自动格式化、替用户决定删哪块盘。

## 8. 回放增强

**要解决的问题**：时间轴能点了，但"想看清那一下"和"想把这一段发给别人"
仍然费劲。

**落地要点**

- 回放变速（0.5× / 1× / 2× / 4×）与逐帧（前后各一帧），跨分段连续。
- **按事件跳转**：时间轴上的事件块可键盘切换（上一个/下一个事件），
  自动把播放头对到事件起点前 2 秒。
- **片段导出**：选起止点（或直接"导出这个事件"）→ 服务端用 ffmpeg 无损拼接
  （同编码直接 copy，跨编码才转），导出进度可查、完成后给下载链接。
- **缩略图预览**：时间轴悬停显示该时刻缩略图（按需生成并缓存，别一次性把盘读穿）。
- 多路同步回放（2~4 路同屏对齐时间）放在最后，先看单路体验是否够用。

**验收**

- 变速与逐帧在跨分段边界不乱序、不黑屏；1× 行为与现在完全一致。
- 导出文件的时长与所选区间误差 < 1 秒，事件导出默认带 2 秒前摇。
- 悬停缩略图在冷缓存下 500 ms 内出图，热缓存 < 100 ms，且不产生大量孤儿文件。

## 9. PWA + Web Push

**要解决的问题**：手机上每次都要开浏览器输地址；事件通知现在只能发到
邮件/IM，系统级提醒还得靠第三方 App。

**落地要点**

- **PWA**：manifest + Service Worker（只缓存壳与静态资源，**不缓存视频流**），
  可"添加到主屏幕"；离线时给一个明确的"当前离线"页而不是白屏。
- **Web Push**：VAPID 密钥对本地生成并落盘；订阅端点存在配置里（每设备一条）。
  推送内容只放"哪一路、什么时间、有没有事件"，**不附画面**，点开再进 App。
- 推送需要 HTTPS 与公网可达（或局域网内可访问的推送服务）；自签证书不满足，
  所以这条路只在"真证书 + 反向代理"的部署形态下完整可用，其余形态明确标注不可用。
- 现有邮件/IM 渠道保持不变，Web Push 是并列的一条，不替代。

**验收**

- 安装到主屏幕后，断网启动显示离线页，恢复网络自动重连。
- 在 HTTPS 域名部署下，事件发生后 10 秒内收到系统通知；点通知直达该事件。
- 没有 HTTPS / 浏览器不支持时，设置页显示"当前环境不可用 + 原因"，不假装成功。

## 10. 多用户与权限

**要解决的问题**：现在一个密码管全部。家里多人看、或给老人/保姆开"只能看某几路"，
都做不到；出问题也无法区分是谁在看。

**落地要点**

- 账号模型：用户名 + 密码（沿用 PBKDF2），角色 **管理员 / 观看 / 回放**；
  可按摄像头授权（例如只给"客厅"）。默认仍只建一个管理员，升级不改行为。
- 权限落到接口层（不是藏按钮）：直播流、回放文件、事件、设置、云台、对讲
  各自校验；未授权的摄像头在列表与时间轴里直接不出现。
- 会话与审计打通：每条会话带用户名，审计日志（见第 6 项）记录"谁"。
- 登录限流按"IP + 用户名"继续沿用；管理员可强制下线某条会话。

**验收**

- 观看账号：能看授权摄像头直播与回放，访问未授权路径返回 403（含直接拼 URL、
  直接拉 `/rec/...`、`/api/events` 三种绕法）。
- 回放账号不能改设置、不能动云台；管理员可以。
- 升级现有安装：不配置多用户时行为与 1.2.0 完全一致，原密码继续可用。

**明确不做**：LDAP/OAuth 集成、按时间段授权、密码找回邮件（自建场景没有可靠
邮件通道，管理员重置更诚实）。
